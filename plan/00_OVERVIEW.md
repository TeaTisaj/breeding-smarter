## 1. What we are building

A proof of concept (POC) with four parts:

1. **A synthetic, calibrated, multi-breed dog pedigree dataset** (registry-style tables plus a separate hidden "ground truth" table), generated by an open, seeded, configurable simulator. Nothing in it is a real animal.
2. **A pedigree analytics engine**: inbreeding (F), kinship, mean kinship (MK), genetic diversity (GD), effective population size (Ne), founder contributions, pedigree completeness.
3. **A rule engine plus mate recommender**: hard compliance checks (EU Regulation 2026/1818, FCI, Kennel Club UK, Raad van Beheer NL, HKS Croatia profiles) and an explainable multi-factor score for each candidate pair (inbreeding, diversity, Mendelian disease risk, breeding values, sire overuse, pedigree completeness).
4. **Evidence and demo**: multi-generation simulation experiments comparing breeding strategies, an interactive web demo, a published dataset with a DOI, and conference materials (poster, slides, optional short paper).

**Species-agnostic by design.** Everything species-specific (litter size, generation interval, breeding ages, rules) lives in YAML config, not code. Dogs are the only species implemented for the conference. A horse profile is a stretch goal used to back the "and beyond" claim.

### 1.1 The one-sentence pitch
> Kennel clubs today have lookup tools (what is this dog's COI?), not decision tools (which mate best protects this breed?). We built an open, explainable, rule-aware matching engine and a realistic synthetic benchmark to prove it, and we are looking for partners with real data.

### 1.2 Novelty claim (what to defend at the congress)
No existing tool combines all of these in one open package (see `docs/research.md` section 5):
1. Multi-jurisdiction rule enforcement, including the new EU Regulation 2026/1818.
2. Population-aware ranking (mean kinship), not COI alone.
3. Carrier-aware Mendelian risk and breeding values in the same score.
4. An exact, additive explanation of every pair's inbreeding (which ancestors cause it).
5. A documented, validated synthetic benchmark dataset with ground truth that others can reuse.

## 2. Scope

Tags used in every phase file:
- **[MVP]** required for the conference. Must be done and tested.
- **[STRETCH]** only if MVP for the whole project is done and there is time left. Never start a STRETCH task while any MVP task is open, unless Tea says so.
- **[HUMAN]** a task only Tea or her colleague can do (emails, verifying legal text, printing). Claude Code prepares material for it but does not mark it done.

### 2.1 In scope (MVP)
- Python package `breeding_smarter` with CLI.
- Simulator for 3 synthetic dog breed archetypes, about 140k registered animals (plus the hidden history), 1980 to 2026.
- Registry tables (observed) plus ground-truth tables (true breeding values, true identity-by-descent inbreeding, full genotypes).
- Calibration targets and an automatic validation report (target vs simulated).
- F, kinship, MK, GD, Ne (two methods), founder contributions, effective number of founders (fe), founder genome equivalents (fg), completeness (equivalent complete generations).
- Rule engine with 5 jurisdiction profiles in YAML, each rule tagged with source and verification status.
- Mate recommender with explainable score card.
- Experiments: 5 strategies over 10 generations, replicates, figures.
- Streamlit demo app, deployed to a public URL.
- Dataset and code release (GitHub, Zenodo DOI, Hugging Face mirror) with datasheet.
- Poster, slides, demo script, partner one-pager.

### 2.2 Out of scope for the conference
- Real data of any kind (we use none; we only calibrate to published summary statistics).
- Production backend (Django, Postgres, auth). Planned for after the conference.
- Genomic data (SNP arrays, ROH). The kinship layer is designed to accept an external kinship matrix later.
- Full optimum contribution selection with a QP solver (STRETCH).
- LLM-generated explanations (post-conference idea, see section 9).

## 4. Architecture

```
            configs/*.yaml (species, breeds, rules, scoring, experiments)
                          │
          ┌───────────────┴─────────────────┐
          ▼                                 ▼
   sim/ (simulator)                  rules/ (rule engine)
   market + genetics                        │
          │ writes                          │
          ▼                                 │
   data/generated/<run_id>/*.parquet        │
   (observed tables + truth tables)         │
          │ read via io/ (DuckDB/pandas)    │
          ▼                                 ▼
   pedigree/ (engine: F, kinship, MK, Ne) ──► matching/ (candidates, scoring, explain)
          │                                 │
          ▼                                 ▼
   calibration/ (targets vs simulated)   experiments/ (strategies over generations)
          │                                 │
          ▼                                 ▼
   reports/validation/                 reports/experiments/ (figures, tables)
                          │
                          ▼
                  app/ (Streamlit demo)
```

Key design decisions (write each as an ADR in `docs/decisions/` during P0):
- **ADR-001: Parquet files plus DuckDB, not Postgres, for the POC.** Zero infrastructure, fast analytical queries, trivial to publish. Postgres and Django come after the conference, when there are real users.
- **ADR-002: Streamlit for the demo.** Fastest path to an interactive, deployable, all-Python demo. A Django REST API plus a React front end is the production path later.
- **ADR-003: Custom Python simulator, not AlphaSimR.** We need a breeding market (popular sires, kennels, imports, rule-compliant matings) and pluggable mating strategies. AlphaSimR is R and genome-focused. We can export pedigrees to it later.
- **ADR-004: numba for the hot loops** (Meuwissen and Luo inbreeding, Colleau kinship products). Pure Python reference implementations are kept for testing.
- **ADR-005: The simulator and the experiments share one engine.** Generating history and running future experiments are the same loop with a different `MatingStrategy`. This guarantees experiments start from exactly the dataset we publish.
- **ADR-006: Observed vs truth separation.** The registry tables contain only what a kennel club would know. Truth tables (true breeding values, true IBD, untested genotypes) are separate files and the engine never reads them except in validation and experiments.

## 7. Conventions (Claude Code must follow these)

1. **Determinism.** Every random process takes a `numpy.random.Generator` passed in explicitly. One master seed per run, child seeds via `np.random.SeedSequence.spawn`. Same config plus same seed means byte-identical Parquet output (test this).
2. **Run manifests.** Every generated dataset folder contains `manifest.json`: run_id, git commit, config hash, seed, package version, timestamps, row counts, generator wall time.
3. **Internal IDs.** Animals have an integer `idx` assigned in birth order (parents always have smaller `idx` than offspring). This topological order is required by the pedigree algorithms. Unknown parent is `-1` in int arrays and NULL in Parquet.
4. **Public IDs are visibly synthetic.** Registration numbers start with `SYN-`. Microchip numbers use the ISO 11784 country code `999`, which is reserved for test transponders (verify this in P1, task 1.6). Breed names are fictional (`Synthetic Breed L/M/S`). Kennel and dog names are generated from syllables.
5. **Units.** Inbreeding and kinship are stored as fractions in [0, 1]; the app displays percentages with one decimal place.
6. **No hidden constants.** Every biological or regulatory number lives in YAML with a `source` field (citation key from `docs/research.md`) or `assumption: true`.
7. **Honesty labels.** Any rule not verified against the primary legal text has `verified: false` and the app shows an "unverified" badge next to it.
8. **Tests first for the engine.** For `pedigree/`, write the fixture tests with known answers before the implementation.
9. **Small commits** with conventional messages (`feat(pedigree): ...`, `test(sim): ...`).
10. **Large data is never committed.** `data/` is gitignored. Datasets are published as release assets and on Zenodo.
